# Plugins

Flixer's plugin manager is being introduced in stages. It stores repository and installation metadata in Flixer's PostgreSQL database and stores packages and plugin-owned data under `DATA_PATH/plugins`. The official catalog is `https://github.com/flixermedia/flixer-plugins`.

## Catalog and package format

The catalog root is `repository.json` and declares `manifestVersion: 1`. Catalog entries have a globally unique plugin ID, display metadata, target services, declared capabilities and permissions, and independently versioned releases. A release identifies a plugin manifest, a `.tar.gz` package, a SHA-256 digest, and an optional exact package size. See the versioned schemas in the [official plugin repository](https://github.com/flixermedia/flixer-plugins/tree/main/schemas).

Each package contains `plugin.json` at its root. The package manifest is checked against the catalog manifest before installation. Package paths must be relative; symlinks, traversal paths, duplicate paths, unsupported archive entries, oversized files, and oversized decompressed packages are rejected. Installation is staged and atomically swapped under `DATA_PATH/plugins/installed`; settings and plugin data are kept separately under `DATA_PATH/plugins/data`.

## Permissions and execution

Plugin permission declarations are not treated as isolation. Installation requires explicit administrator approval for every declared permission. Repository manifests are fetched only over HTTPS; the manager rejects redirects and private/reserved DNS answers, pins the request to a validated public address, bounds response sizes, validates schemas, and checks package digests.

Executable extension targets use WASI modules run by the indexer's wazero host, with no preopened filesystem, inherited environment, or network imports; execution has memory, input/output, and time limits. Indexer provider modules receive one versioned JSON request on stdin. Backend route modules use the same isolated runner and receive a versioned JSON request on stdin. Modules have no direct network access; outbound HTTP is available only through the host-call protocol described below.

Plugin settings use the package's JSON Schema. The admin form supports text, numeric, boolean, enum, and primitive-list fields. Fields marked `writeOnly` or `x-flixer-secret` are stored separately using AES-GCM with a key derived from `APP_SECRET`; API reads return a mask, never the saved value. Schema references to external URLs and unsupported form shapes are rejected.

Backend route plugins declare a `flixer` target with a `.wasm` entry and the `api.routes` or `backend.routes` capability. Each operation must also declare and receive administrator approval for its exact `api.routes.{operation}` permission. They are invoked through authenticated `POST /api/plugins/{pluginId}/{operation}` requests, using either a login session token or an API key (which acts as its owner, so `user` and per-user storage are the owner's). The WASI module receives `{ apiVersion, method, operation, user: { id, role }, request: { method, body } }`; when storage-read permissions are granted, the host adds a `storage` snapshot. A module may return `{"result": ...}` or `{"error": {"code": "...", "message": "..."}}`. To persist state, it may also return `storage.plugin` and/or `storage.user` patches shaped as `{ "set": { "key": "value" }, "delete": ["old-key"] }`; each scope requires its matching `storage.{scope}.write` permission and is applied transactionally. Plugin storage is namespaced by plugin; user storage is additionally isolated to the authenticated user. Each scope is limited to 256 KiB and 1,024 keys total. Plugins never receive direct database, filesystem, network, settings-secret, or application-token access. **Host calls.** Instead of a result, a backend module may return `{"hostCalls": [{"id": "a", "op": "http.get", "url": "https://api.example.com/x"}], "continuation": <any JSON>}`. Flixer performs the calls and re-invokes the module with the same request plus `continuation` and `hostResults: [{ id, ok, status, body, error }]`; the module is stateless between rounds, so any state it needs must be carried in `continuation`. Supported operations are `http.get` and `http.post` (a `body` string of at most 16 KiB, sent as `application/json`). Each requires the exact `network.http.{hostname}` permission to be declared and approved, HTTPS on port 443 only, no URL credentials, a publicly routable address (DNS is pinned to the checked address), no redirects, a 4-second timeout and a 256 KiB response limit. A call may fail individually with `permission_denied`, `invalid_url` or `request_failed` without failing the invocation. Limits: 8 calls per round and 4 rounds per invocation. Storage patches are applied only from the final result. Backend plugin errors are isolated to the request and reflected in plugin health state.

**Segment providers.** A plugin with the `media.segments` capability and an approved `media.segments.lookup` permission may supply segments such as intro, recap, credits and preview. Flixer calls its `lookup` operation internally (no public route) with `{ item: { type, durationMs, providerIds, season?, episode? }, baseUrl }` and expects `{ segments: { <type>: { startMs, endMs, submissions } | null } }`: an object stores the segment, `null` clears the plugin-owned value, and an omitted type is left unchanged. Plugin values are kept separately from manual edits and indexed TheIntroDB timings; chapter detection remains local to Flixer. A plugin may configure its service URL through its own settings. Streamer plugin execution is not yet available. The frontend provides repository, installation, and schema-backed settings administration; it does not load third-party UI code.

## Host APIs for backend plugins

Beyond `http.get`/`http.post`, backend modules can use these host calls, each gated by a declared and approved permission. Calls in one round that are not HTTP run in order; HTTP calls run concurrently.

- **`http.request`** (`network.http.{hostname}` or `network.http.any`): `method` GET/POST/PUT/DELETE, up to 8 headers from an allow-list (`authorization`, `x-api-key`, `x-emby-token`, `content-type`, `accept`), and a body up to 64 KiB. The HTTPS/443, public-address, no-redirect and size rules are unchanged.
- **Database** (`database.tables`): the manifest's `database.tables` declares columns (`text`, `integer`, `boolean`, `timestamp`, `json`, `uuid`) and indexes. Flixer creates missing tables, columns and indexes on first use under hashed names and never drops anything. Plugins use `db.find`, `db.count` (optionally `groupBy`), `db.insert` (up to 50 rows), `db.update` and `db.delete` (a non-empty `where` is required) with structured `where` filters (`eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `like`, `ilike`, `isnull`, `notnull`; an array is AND, or `{all, any}`). There is no raw SQL and `limit` is capped at 200.
- **Secrets** (`secrets.manage`): `secret.set` / `secret.get`, encrypted per plugin.
- **Users** (`users.read`): `users.get` and `users.list` return id, username, display name and role only.
- **Library** (`library.read`): `library.match` maps result cards to existing library items by provider id or title and year.
- **Notifications** (`notifications.send`): `notify.send` to one user or all admins, with a relative link.
- **Settings** (`settings.read`): the envelope carries the plugin's effective settings, with defaults applied and secrets decrypted. The envelope also carries `now`.
- **Schedules** (capability `schedule`, permission `schedule.run`): each `schedules` entry (`operation`, `intervalSeconds` 60–86400) is invoked as user `{id: "system", role: "system"}` while the plugin is enabled. Timing is in-memory per Flixer process, so multiple instances may each run it.
- **Search** (capability `search.results`, permission `api.routes.search`): the main search page calls `GET /api/plugins/search?q=&type=`, which invokes each such plugin's `search` operation with `{ q, type? }` and expects `{ sections: [{ title, items: [{ title, subtitle?, poster?, shape?, badge?, page, query }] }] }`. Items link to the plugin's own page; posters must be HTTPS and the result is sanitized by Flixer.
- **Pages** (capability `ui.pages`, permission `api.routes.page`): `ui.pages` entries appear at `/plugins/{pluginId}/{pageId}` (and in the main navigation when `nav` is `main`; `adminOnly` hides them from non-admins). The web app calls the `page` operation with `{ page, query }` and renders the returned `{ title?, view }` JSON tree (layout, content, input and navigation nodes). Buttons and forms invoke other operations and the response may carry `toast`, `navigate`, `reload` or `error`. Plugins ship no browser code. `GET /api/plugins/pages` lists the visible pages.

## Lifecycle and data

The admin Plugins page can list installations, search enabled repository catalogs, filter by target and capability, add/refresh/remove custom repositories, install releases, configure schema-backed settings (each plugin with a settings schema has a **Settings** button that opens a dedicated page generated from the schema), and enable/disable/uninstall supported indexer and backend route plugins. Newer releases are discovered from cached catalogs and can be applied manually to disabled plugins. Updates preserve settings, encrypted secrets, and grants for permissions still requested by the new release. Every install or update attempt is recorded in `plugin_update_history`; successful package and installation metadata changes are committed together, and failures retain a bounded, credential-redacted diagnostic. Admins can inspect the latest 20 attempts from each installed plugin's **History** control or use `GET /admin/plugins/:id/history?limit=20` (limit 1–100). History remains after plugin uninstall. Every update is verified and staged, and the prior package is restored if metadata persistence fails. Automatic updates are not implemented. The official repository is seeded idempotently and cannot be removed. Catalog refresh runs in the background at startup and periodically; a repository outage does not block Flixer startup.

Installed metadata records requested versus granted permissions. Backend and indexer WASI modules currently receive no host capabilities; backend authentication is enforced by Flixer before dispatch. The signed indexer status endpoint reports runtime registration; per-invocation health metrics, publisher signatures, and app-version checks for streamer/web targets remain pending.

Uninstall removes the package but retains plugin-owned data, including scoped backend storage, for a future reinstall. Existing user feature data is not migrated by the current plugin manager yet. Media requests and theme songs remain core-owned.
